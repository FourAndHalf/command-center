Personal Command Center: Delivery Plan

Experience → Decision → Prediction → Outcome → Review → Learning → Future Decision. Angular website and Flutter mobile app on one Go + PostgreSQL backend, self-hosted so it is reachable from anywhere.

BackendGo modular monolith, REST + OpenAPI
DatabasePostgreSQL, pgvector, FTS
WebAngular, Tailwind, CDK
MobileFlutter (iOS + Android)
FilesMinIO (S3-compatible)
HostingOne VPS, Docker Compose, Caddy TLS

Ground rules

  • Every change is developed on a feature branch, merged to main, and the branch is deleted.
  • OpenAPI is the single contract. Web and mobile use generated clients; CI fails on drift.
  • Decisions and reviews are immutable history. AI output is always a draft until the user confirms.
  • The product must stay fully useful with AI disabled.
  • Time estimates assume one developer working part-time-to-full-time; treat them as relative sizes.

Repository layout

backend/    Go API + worker, migrations, openapi.yaml
web/        Angular app
mobile/     Flutter app
deploy/     docker-compose, Caddyfile, backup scripts
docs/       spec, design docs, this plan

Roadmap at a glance

  1. M0 Foundations: design docs, scaffold, CI 1-2 wk
  2. M1 Core backend: decisions, versions, relations 2-3 wk
  3. M2 Review loop: reviews, scheduler, notifications 2-3 wk
  4. M3 Auth + first web milestone 3-4 wk
  5. M4 Deploy: live on a VPS, reachable anywhere 1 wk
  6. M5 Flutter mobile app 4-5 wk
  7. M6 History: timeline, search, sources, files 3-4 wk
  8. M7 AI layer (optional, off by default) 3-4 wk
  9. M8 Integrations 3-4 wk
  10. M9 Hardening: security, export, observability 2-3 wk

Usable checkpoints: end of M3 is the first complete decision loop on web; end of M4 is real use from any device; end of M5 adds mobile.

M0

Foundations

1-2 weeks

Agree the design on paper, then stand up an empty but healthy system.

Deliverables

  • DOCSArchitecture overview, domain model, PostgreSQL schema, ER diagram, review state machine, ingestion architecture, AI architecture, API outline, frontend information architecture
  • DOCSCommit docs/prompt.md and these design docs
  • BEGo module with one folder per domain module: decisions, reviews, events, sources, entities, goals, search, notifications, ingestion, ai
  • BEConfig loading, structured logging, /healthz and /readyz, migration runner
  • OPSdocker-compose.yml with Postgres + pgvector and MinIO; Makefile with build, test, lint, migrate, run
  • OPSCI: build, vet, test on every PR; OpenAPI lint
  • DOCSFill in the Commands and layout sections of AGENTS.md

Exit criteria

  • docker compose up gives a healthy /healthz and migrations apply to an empty database.
  • CI is green on a trivial PR.

Depends on

Nothing.

Risks

Over-designing on paper. Keep docs short and revise them as code lands.

M1

Core backend

2-3 weeks

Store decisions the way the spec demands: structured, versioned, never rewritten.

Deliverables

  • BEMigrations: decisions, decision_versions, assumptions, events, entities, relations, goals, audit_log (UUID keys, foreign keys, indexes; JSONB only where flexible)
  • BEDecision CRUD with all spec fields: context, objective, alternatives, constraints, assumptions, emotional context, expected outcome, success and failure criteria, confidence, importance, reversibility, tags
  • BEImmutable versioning: any material edit writes a new version, v1 is never destroyed
  • BERelations: supersedes, modifies, reverses, depends_on, influenced_by, resulted_in, contradicts, supports; decision-to-goal links
  • BEEvents and entities CRUD
  • BEAudit log entries on every write
  • BERealistic seed data (career, technical, financial decisions with assumptions)
  • APIopenapi.yaml published as the source of truth

Exit criteria

  • Tests pass for decision creation, versioning (v1 preserved), and relations.
  • Seed data loads and the API returns a full decision with assumptions and relations.

Depends on

M0.

Risks

Schema churn. Keep the core model small and add fields by migration, not by speculation.

M2

Review loop

2-3 weeks

Make the system come back to you: schedule reviews, remind reliably, keep history.

Deliverables

  • BEDecisionReview (append-only) with all spec fields, plus assumption validation updates
  • BEReview schedules: time-based, event-based, and condition-based triggers; next_due_at, last_completed_at, snoozed_until; snooze never loses the original due date
  • BEPostgres-backed job queue and Go worker with leasing, retries, and backoff
  • BENotifications: in-app and email; idempotent, deduplicated, retryable, auditable
  • BEOverdue handling: stays visible until completed or dismissed
  • BECompleting a review can schedule the next one

Exit criteria

  • Tests cover due dates, recurrence, snoozing, retries, and duplicate prevention (a crashed worker never double-notifies).
  • End-to-end via API: create decision, set review, worker fires notification, complete review, next review scheduled.

Depends on

M1.

Risks

Duplicate notifications from worker restarts. Use unique idempotency keys per (schedule, due date) enforced in the database.

M3

Auth + first web milestone

3-4 weeks

Deliver the spec's first milestone on the website: the full create-to-learn loop.

Deliverables

  • BESingle-user auth: hashed password, secure cookie sessions for web, short-lived access + refresh tokens for mobile, rate-limited login, TOTP as a second factor
  • BEAuthorization on every endpoint; audit log of logins
  • WEBAngular + Tailwind app shell; primary navigation: Today, Decisions, Reviews, Timeline, Search
  • WEBGenerated TypeScript API client from OpenAPI
  • WEBToday screen: reviews due, overdue, active decisions, upcoming, unresolved
  • WEBFast decision capture form (under a minute) with assumptions and expected outcome
  • WEBDecision Replay view: why, knew, believed, felt, expected, what happened, reviews, what changed, related; original visually distinct from later reviews
  • WEBReview workflow: optional questions, expected vs actual, assumption verdicts, lesson, next review

Exit criteria

  • Manually complete the whole loop in the browser: capture, assumptions, expected outcome, review date, receive review, record actual outcome, lesson, next review, view history.
  • Angular unit tests for core components; API tests for auth flows.

Depends on

M1, M2 (review endpoints can land during M3).

Risks

Auth mistakes are costly once the app is public. Prefer proven libraries and review the session and token design before M4.

M4

Deploy: reachable anywhere

1 week

Put it on the internet safely so real use, and mobile development, can start.

Deliverables

  • OPSVPS provisioned, firewall, SSH keys only, unattended security updates
  • OPSDomain and DNS; Caddy reverse proxy with automatic TLS; HTTPS only
  • OPSProduction Docker Compose: API, worker, Postgres, MinIO, Caddy; secrets outside the repo
  • OPSEncrypted nightly backups of Postgres and MinIO copied off the box
  • OPSDeploy script or CI job; documented runbook in deploy/
  • OPSUptime check on /healthz

Exit criteria

  • Log in over HTTPS from a phone browser on mobile data.
  • A backup restore drill succeeds on a fresh machine.

Depends on

M3.

Risks

Personal data on a public host. Do not load real data until backups are proven and login rate limiting is on. A single VPS is a single point of failure, so restore drills matter.

M5

Flutter mobile app

4-5 weeks

Capture and review from your pocket, with the same data and rules as the web.

Deliverables

  • MOBFlutter project, generated Dart API client from OpenAPI, state management, theming
  • MOBLogin with secure token storage (Keychain / Keystore) and refresh handling; biometric unlock
  • MOBToday screen
  • MOBQuick capture, under a minute; drafts saved locally; offline queue that syncs using idempotency keys
  • MOBDecision detail (replay view) and review completion
  • MOBRead cache so recent decisions open offline
  • BEDevice registration and push delivery via FCM/APNs, added to the notification module with email fallback
  • MOBPush tap deep-links to the review
  • MOBTimeline and Search screens once M6 endpoints exist
  • OPSTest builds via TestFlight and Play internal testing

Exit criteria

  • On a real device against the deployed API: capture a decision offline, sync it, receive a review push, complete the review.
  • flutter test passes; CI builds both platforms.

Depends on

M4 (deployed API), stable OpenAPI from M1-M3.

Risks

Apple developer account and push setup lead time; offline conflict handling (keep captures append-only to avoid conflicts); web and mobile drifting apart, so both stay thin over the API.

M6

History: timeline, search, sources, files

3-4 weeks

Answer "how did I arrive at this?" and find anything, with provenance on every result.

Deliverables

  • BESource model with content hash, external id, and permissions; provenance links from every record back to its source
  • BEFile attachments through MinIO with signed URLs
  • BETimeline endpoint (events, decisions, reviews, milestones) with filters: date, life area, type, entity, importance, status
  • BEHybrid search: Postgres full-text plus pgvector plus structured filters; embeddings behind a provider interface with a local option
  • BE"How did I arrive here?" graph walk over relations
  • WEBTimeline, Search, Sources, Goals, and related-records panels
  • MOBTimeline and Search on mobile

Exit criteria

  • A natural-language query finds a decision by meaning, and the result shows its source.
  • Filtering the timeline by decision type and date range returns correct results.

Depends on

M1, M4.

Risks

Embedding provider lock-in. Store the model name with each embedding so vectors can be regenerated.

M7

AI layer

3-4 weeks

Add four explicit AI capabilities. No autonomous agent, nothing canonical without confirmation.

Deliverables

  • BEProvider-agnostic AI interface; external providers disabled by default and enabled explicitly, with a clear statement of what data is sent
  • BEAI capture: free text to a draft decision; unknown fields marked unknown; user confirms before a canonical record is created
  • BEAI retrieval: natural-language questions with citations, labelling recorded fact, user statement, AI inference, unknown
  • BEAI review: compare expected and observed outcome, surface discrepancies, ask questions; no personality analysis
  • BELongitudinal analysis: traceable statements such as "in 6 recorded decisions..."
  • BEAI-extracted fields flagged and never treated as canonical until confirmed
  • WEBMOBDraft review screens, citation display, AI settings

Exit criteria

  • Tests cover structured extraction validation, unknown-field handling, provenance, and citation generation.
  • Turning AI off leaves every other feature working.

Depends on

M6.

Risks

Hallucinated history. Validate every output against a schema, require citations, and reject answers that cite nothing.

M8

Integrations

3-4 weeks

Feed more evidence in through one ingestion pipeline. Connectors hold no business logic.

Deliverables

  • BEIngestion pipeline: raw source, normalize, deduplicate, extract, candidate record, human confirmation, canonical record, relations, search index, optional review schedule
  • BEIdempotency keys and content hashes
  • BEWave 1: manual capture, Markdown import, file upload, voice capture, calendar
  • BEWave 2: GitHub, Gmail/Outlook, browser extension
  • WEBMOBCandidate inbox to confirm or reject extracted records

Exit criteria

  • Importing the same file twice creates one source.
  • Nothing enters canonical records without confirmation.

Depends on

M6, ideally M7 for extraction.

Risks

OAuth scope creep and provider policy. Request read-only scopes; no always-on recording or ambient monitoring.

M9

Hardening

2-3 weeks

Make it trustworthy for years of personal data.

Deliverables

  • BEFull export: JSON, Markdown, CSV, original attachments, relations and review history, readable without the app
  • BEComplete deletion of all data on request
  • BERate limiting, security headers, dependency scanning, secret rotation, encrypted backups verified
  • OPSOpenTelemetry traces and metrics, structured logs without raw personal content, job monitoring and alerts
  • OPSScheduled restore drills; load test; security review
  • WEBMOBExport and delete controls in Settings; accessibility pass
  • MOBStore release: App Store and Play Store (or keep private distribution)

Exit criteria

  • Export, wipe, and re-import round-trips with no loss.
  • Definition of done from the spec (12 items) is met.

Depends on

All prior milestones (start earlier items in parallel).

Risks

Leaving hardening to the end. Auth, backups, and log hygiene are already required in M3-M4; M9 is verification and depth.
